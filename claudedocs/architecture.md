# Архитектура каркаса фреймворка sorting-lab

Дата: 1 ноября 2026 г. Документ описывает каркас проекта и обоснование
принятых решений; актуальные правила работы — в CLAUDE.md в корне проекта.

## Принятые решения

| Вопрос | Решение | Обоснование |
|---|---|---|
| Язык | Чистый Python 3.12+ | Скорость разработки, читаемость для математиков; сравнение алгоритмов по числу сравнений, а не по секундам |
| Структура | src-структура | Стандарт экосистемы; защита от случайного импорта не той версии пакета |
| Зависимости | numpy, matplotlib; dev: pytest | numpy — большие массивы и распределения; matplotlib — будущие графики |
| Данные | Генераторы с зерном + эталонные случаи | Воспроизводимость без хранения больших файлов; крайние случаи ловят типовые ошибки |
| Контроль версий | Локальный git | Два соавтора; статьи из papers/ закоммичены, сам архив .7z исключён как дубликат |
| Комментарии | Русский | Статьи и обсуждения на русском; так быстрее сверять код с теорией |

## Слои каркаса

Слой 1 — контракты (`base.py`). Класс `Algorithm` задаёт единый интерфейс:
`sort(data, compare)` сортирует изменяемую последовательность на месте,
сравнивая элементы только через компаратор — функцию, возвращающую
отрицательное/нулевое/положительное число. Паспорт `AlgorithmInfo` хранит
формальные сведения из статьи: оценки сложности, устойчивость, работу
на месте. Всё, что дальше (реестр, тесты, стенд), опирается только на эти
контракты.

Слой 2 — алгоритмы (`algorithms/`). Один файл на сортировку. Heapsort
служит эталоном оформления и строительным блоком для Introsort (метод
`sort_range` сортирует участок массива). Реализованы также introsort
(Musser, 1997), powersort (Munro, Wild), splitsort (Levcopoulos, Petersson,
1991) и adaptive_heapsort (Levcopoulos, Petersson, 1993). Если метод `sort`
новой заготовки бросает NotImplementedError, тесты её прозрачно пропускают.

Слой 3 — данные (`datasets/`). Шесть генераторов: случайный, отсортированный,
обратно отсортированный, почти отсортированный (доля сбоев — параметр),
с малым числом уникальных значений, пилообразный. Каждый принимает размер,
зерно и хранится в словаре GENERATORS для перечисления. Двенадцать эталонных
крайних случаев покрывают пустой массив, короткие входы, равные элементы,
отрицательные числа, строки.

Слой 4 — измерительный стенд (`bench/`). `CountingComparator` оборачивает
любой компаратор и считает вызовы. `measure` прогоняет алгоритм на копии
данных и возвращает RunMetrics: имя алгоритма, набор данных, размер, число
сравнений, время, признак совпадения с эталонной sorted(). Отдельно
`count_inversions` считает инверсии входа слиянием за O(n log n) — мера
отсортированности, через которую формулируются оценки адаптивных алгоритмов
Лефкопулоса—Петерссона. Метрики не финализированы; архитектура позволяет
добавлять новые поля RunMetrics, не трогая алгоритмы.

Слой 5 — реестр (`registry.py`). Словарь «имя — алгоритм»; `register`
защищён от дублирования имён, `implemented_algorithms` фильтрует заготовки
пробным прогоном. Тесты и стенд ходят только через реестр, поэтому новый
алгоритм подхватывается везде автоматически.

## Ход работы с харнессом

CLAUDE.md в корне загружается в контекст агента при каждом сеансе и содержит
правила проекта и текущий этап. Хук в `.claude/settings.json` после каждого
редактирования файлов проекта автоматически запускает pytest и возвращает
результат агенту: сломанный код замечается сразу, а не при ручном запуске
тестов.

## Как добавлять алгоритм

1. Новый файл в `src/sorting_lab/algorithms/` по образцу heapsort.py
   или любому другому реализованному алгоритму.
2. Импорт и `register(ИмяКласса())` в `algorithms/__init__.py`.
3. Тесты корректности подхватят алгоритм сами; отдельных тестов писать не
   нужно, если у алгоритма нет специфических инвариантов. Если в паспорте
   указано `stable=True`, автоматически проверяется и устойчивость.
